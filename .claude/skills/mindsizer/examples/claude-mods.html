An explanation of Claude Code mods, from the official docs, the launch post (Oct 1, 2026) and the GitHub design discussion

Claude Code mods: small functions that change how Claude Code works

Everything Claude Code does, like calling a tool or drawing the screen, fires an event. A mod is a few lines of TypeScript or JavaScript that hooks an event and lets it pass, changes it, or answers it itself, with your permissions.

Inside Claude Code

A mod is a plugin whose code runs inside Claude Code, not beside it

Settings hooks, skills, status lines and MCP servers work from outside Claude Code: each runs a script, or hands Claude text or tools. A mod runs inside Claude Code, so it can draw a pane or rewrite a tool call before it runs. It ships in a plugin, so you install and share it like one.

The others hand Claude Code something. A mod changes Claude Code itself.

more: the three files, where mods run, the name

A small mod is three files: .claude-plugin/plugin.json (the plugin manifest), hooks/hooks.json (whose modules key points at your code, which is what makes the plugin a mod), and the hooks module, such as hooks/register.js. Claude Code loads .js and .ts directly, with no Node.js, bundler or build step.

A mod is a plugin, so you install, update and share it like one: /plugin install token-chart@your-org, a marketplace, or Anthropic's directory. One plugin can hold a mod, a skill and an MCP server together.

Mods work in the Claude Code CLI and in the Code tab of the Desktop app. Their hooks also run in the VS Code extension's chat panel, claude -p, the Agent SDK and cloud sessions (for a plugin that reaches the cloud session), but anything they draw shows only in the terminal and the Desktop app. Plugins, and so mods, aren't available in WSL sessions of the Desktop app.

The design was first posted on GitHub on Sep 3, 2026 as "function hooks", modelled on Express and Koa middleware. On Sep 9 the product name became Claude Mods; "function hook" stays the name of the primitive mods are built on.

Inside Claude Code›Hooks on events

Each hook gets an event and decides: let it pass, change it, or answer it itself

A mod calls on('tool.call', hook) to register a hook, a function that runs when that event happens. It gets the event and next, which hands the event on to the rest of Claude Code. Say Claude wants to run git push --force. Pick what your hook does.

One function, three choices: call next(e), call it with a changed copy, or don't call it.

  
more: the three arguments, matchers, the docs' first mod
    

      
Every hook receives the same three arguments: $, the mods API (next section); e, the event as frozen plain data, so to change it you pass a copy to next; and next, which runs the hooks after yours and then Claude Code's own behaviour, and resolves to the result.

      
A second argument to on is a matcher, a filter on the event's fields: on('tool.call', { tool: 'Bash' }, hook) runs only for Bash.

      
The docs' first mod uses all three choices at once. A tool.call hook counts each call and passes it on (observe). A ui.render hook on the spinner adds · tool calls: 3… after its word (rewrite). A command.run hook answers a new /tally command with the count and never calls next (answer).

      
Events cover tools (tool.call, tool.check), prompts and what Claude reads (prompt.submit, prompt.section), commands, turns (turn.step, one request to the model), sessions, subagents, the interface, other mods loading, and every settings hook event as classic.<Event>. A hook runs for at most 10 seconds of its own time per event.

    

  






  
Hooks on events›Drawing

  
A mod can draw its own interface and redraw Claude Code's, but not the permission prompt

  

    
Drawing the screen is an event too (ui.render), so a mod can add new places or restyle Claude Code's own. It can't change what a permission prompt shows you. Built-in features like /diff are mods themselves, so you can switch them off or replace them. Pick a place.

more: render sites, elements, the built-in /diff
    

      
The places are called render sites: Pane, AbovePrompt, UserMessage, AssistantMessage, ToolUse, ToolResult, AskUserQuestion (the dialog Claude asks questions in), Spinner, PromptHint and a few more. A hook builds what it draws from elements such as Box, Text, Button, Input, Select and Markdown; Svg draws only on the Desktop app, Raster and Image only in the terminal.

      
When you press a mod's button, that fires ui.press, and other mods can respond to it. For a single line without drawing, $.ui.status puts one under the prompt, $.ui.toast a notification, $.ui.log a dim transcript line Claude doesn't read.

      
Some of Claude Code's own features are mods now. /diff is the built-in mod cc-plugin-diff: disable it in /plugin or replace it with your own. Anthropic plans to move more built-in features to mods, "so you can pare Claude Code down to a small core and add back only what you want".

    

  






  
Hooks on events›Your permissions

  
Everything a mod does beyond its own code goes through $, with your permissions

  

    
A mod's code has no file, network or process access of its own. It reaches everything through the mods API, the $ each hook receives, and behind $ it can do what you can: mods aren't sandboxed. It can also approve a tool call before you'd be asked: one an ask rule would prompt for, or one your own PreToolUse hook blocked, and in auto mode it skips the classifier. Your deny rules and your organization's managed hooks still win where the built-in guard loads.

$ claude plugin validate ./first-mod

  ❯ ./register.js calls: $.command.register, $.ui.invalidate

  
A mod runs with your permissions and can approve on your behalf, so install only mods you trust, and read their calls: line first.

  
more: what a mod can reach, which calls to look for
    

      
Once loaded, a mod can read your environment variables and settings (API keys included), see every prompt and tool call, rewrite them, submit a prompt as if you typed it, message another of your sessions, approve a tool call before you're asked, and spend your usage on model calls. Turning on sandboxing doesn't contain it: a process a mod starts runs outside the sandbox. Install mods only from authors and marketplaces you trust.

      
In the calls: line, look for $.fs.read/write, $.process.run/spawn, $.http.fetch, $.env.get, $.settings.read, $.model.complete, $.prompt.submit and $.session.send. In the hooks: line, tool.call and prompt.submit mean it sees and can change every tool call and prompt; tool.check means it can approve or deny a call before a permission prompt appears.

      
Claude Code refuses to load a mod that uses $ in a way the analysis can't read, such as const ui = $.ui or $[name]. Each $ call is itself an event (fs.read, http.fetch…), so a mod earlier in the chain can watch, change or refuse it. That is how an organization limits what mods reach.

    

  






  
Your permissions›Stacked

  
When several mods hook one event, they nest: the first to load sees the event first and the result last

  

    
Each hook reaches the rest through next, so mods wrap one another like layers of an onion, and load order decides what each sees. Take an audit log that records each result and a redactor that blanks secrets out of tool output, while Claude reads a .env file.

Order is nesting, so going first means control: you see everything, and you have the last word on the way out.

  
more: tiers, the built-in guard, deny rules
    

      
Mods run in priority groups called tiers: prepend (your organization's, first), user (the ones people install), append, builtin, then Claude Code's core. Administrators set the first and third with prependPlugins and appendPlugins in managed settings. In the design discussion, the author called it an "onion model": a mod further down can't stop one above it.

      
On Team and Enterprise plans, and on any machine with managed settings, a built-in mod called sec-default ("security default") loads ahead of every mod a user installs. It stops users' mods from overriding your permission deny rules and from changing what the organization manages: managed hooks, the system prompt, managed instructions, managed MCP servers. Everything else stays allowed, and it doesn't cover a mod's own $.fs and $.process calls. Its source is public.

      
A PreToolUse hook in managed settings runs before any mod sees the tool call, and its block is final. Settings hooks keep working alongside mods; nothing about them is deprecated.

    

  






  
Stacked and switched›Switched off

  
You can turn mods off one at a time, for one session, or everywhere

  

    
Mods need Claude Code v2.1.287 or later, and from there they're on by default. Each switch reaches further than the last.

  

  

    
switchwhat stopswho sets it

    
      
/pluginOne mod, built-in ones like /diff included.you

      
--safe-modeEvery installed mod and your other customizations, for one session.you

      
disableAllHooksEvery mod you installed, plus your settings hooks and status line, in every session.you

      
allowManagedModsOnlyUsers' own mods; the organization's still load.an administrator

      
disableAllHooks (managed)Every mod and every settings hook, the organization's included.an administrator

    
  

  
Pick the narrowest switch that does the job.

  
more: the old flag, checking what loaded, sideloading
    

      
The early-access flag CLAUDE_CODE_ENABLE_FUNCTION_HOOKS is now ignored, so setting it to 0 doesn't keep mods off.

      
To see which mods a session loaded, run /plugin: a dim line under the tabs reads, for example, 1 mod active · first-mod (built-in mods aren't counted there). To check whether a mod caused a problem, start a session with claude --safe-mode.

      
disableAllHooks and allowManagedModsOnly stop the mod but leave the rest of its plugin: its skills, commands, agents and MCP servers still load. disableSideloadFlags in managed settings rejects --plugin-dir and keeps mods Claude writes during a session from loading.

      
An administrator turns on allowManagedModsOnly as an option on the built-in guard, under pluginConfigs → cc-plugin-sec-default@builtin → options in managed settings. The same entry in a user or project settings file changes nothing. A mod counts as the organization's only when managed settings enable it from a marketplace directory on the machine itself; a plugin copied from GitHub, git, a URL or npm counts as a user's.

    

  






  
Three uses

  
Three things worth building, each using a different power: a guard, a gauge, and a chart

  

    
You don't have to write them by hand: describe one ("make a mod that…") and Claude writes it and, once you approve, loads it for that session.

  

  

    
tool.call · answers
Hold a risky command
A force push or rm -rf waits for your yes; on "no" the hook denies it (the sample mod blast-radius).
Why a mod: it can show what would change and wait for you.

    
a timer · $.process · $.ui.status
Watch CI from the prompt
Every minute it runs gh pr checks and updates a line under the prompt (the API docs' example).
Why a mod: it runs on its own clock, between turns.

    
turn.step · ui.render pane
Chart your context
One hook records your context use after each request; another charts it in a pane (the docs' example).
Why a mod: only a mod can add a pane.

  

  
Guard what Claude does, show what's going on, and add a view of your own: each is one or two hooks.

  
the code for the three
    

      
// a guard (illustrative sketch; RISKY is your own pattern; $.ui.ask's options are in the types beside your mod)
on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
  if (!RISKY.test(e.command)) return next(e)
  const yes = await $.ui.ask(/* question, options */)
  return yes ? next(e) : { deny: 'Cancelled by you' }
})

      
// a gauge (from the mods API docs; summarize is your own)
on('session.start', async ($, e, next) => {
  $.clock.every(60_000, async () => {
    const status = await $.process.run(['gh', 'pr', 'checks', '--json', 'state'])
    $.ui.status('checks: ' + summarize(status.stdout))
  })
  return next(e)
})

      
// a chart (illustrative sketch; turn.step hooks are async generators)
const samples = []
on('turn.step', async function* ($, e, next) {
  yield* next(e)                          // the request runs
  samples.push(await $.session.usage())   // context use after it
  $.ui.invalidate()                       // redraw the pane
})
on('ui.render', { component: 'Pane' }, async ($, e, next) => /* draw samples */)
